# 运维手册

## 角色边界与高风险控制

- 所需权限：受控启停、备份恢复、证书/密钥轮换和应急恢复；不得作质量裁决、登记/批准模型或删除审计记录。
- 操作原因：恢复、回滚、证书吊销、密钥轮换和紧急账号必须绑定工单原因。
- 二次确认：S1 操作由安全、质量或发布负责人中的独立角色确认。
- 审计事件：命令、工单、执行人、确认人、目标、前后状态和验证结果完整记录。

目标、备份、签名、权限或审计状态未知时停止并保持 `HOLD`，禁止无范围删除或静默继续。

受众：系统管理员和运维人员。权限：用户、设备、配置、部署和故障处理。禁止：默认提交质量复核或修改标签。

## 1. 系统启停

### 1.1 启动顺序

按以下顺序启动（每步确认健康后继续）：

1. **数据库**（PostgreSQL）：确认主库可读写，复制延迟在容许范围内。
2. **消息队列**（RabbitMQ）：确认集群所有节点运行，镜像队列同步。
3. **对象存储**（MinIO 或 S3 兼容服务）：确认桶存在且可读写。
4. **业务后端 API**：确认 `/health` 返回 200，数据库和消息队列连接正常。
5. **推理服务**：确认模型加载成功，GPU/CPU 资源就绪，`/health` 返回 200。
6. **前端 Nginx**：确认静态资源可访问。
7. **采集端代理**：在工控机上按顺序启动采集代理，确认与中心连接正常。

启动命令：

```bash
docker compose -f deploy/compose/production.yml up -d
```

### 1.2 关机顺序

按以下顺序关机（倒序停止）：

1. 采集端代理：逐台停止，确认最后采集任务已完成上传。
2. 推理服务：停止请求接收，等待进行中推理完成。
3. 业务后端 API：停止请求接收，等待进行中事务提交。
4. 前端 Nginx。
5. 消息队列：等待消费者确认已处理的消息。
6. 对象存储。
7. 数据库：确认无活动连接后执行检查点并关闭。

关机命令：

```bash
docker compose -f deploy/compose/production.yml down
```

### 1.3 重启

- 单个服务重启：使用 `docker compose restart <service>`。
- 全系统重启：按关机顺序停止，再按启动顺序启动。
- 重启后执行全量健康检查。

## 2. 健康检查

### 2.1 端点说明

| 端点 | 服务 | 检查内容 |
|------|------|----------|
| `/health` | 业务后端 | 数据库连接、消息队列连接、内存使用、线程池状态 |
| `/health` | 推理服务 | 模型加载状态、GPU/CPU 可用、内存占用 |
| `/health` | 对象存储 | 桶可访问性 |
| `/alive` | RabbitMQ | 节点运行状态、磁盘水位、内存水位 |
| `/health` | 采集代理 | 相机连接、磁盘水位、中心连接状态 |

### 2.2 综合健康检查

```bash
curl -s http://localhost:8080/health | jq .
```

健康返回示例：

```json
{
  "status": "UP",
  "database": "UP",
  "messaging": "UP",
  "storage": "UP",
  "inference": "UP",
  "disk_usage_percent": 45
}
```

任何组件返回 `DOWN` 或 `UNKNOWN` 时参照对应故障手册处置。

## 3. 备份验证

### 3.1 验证流程

1. 检查最近一次备份作业的完成时间和状态（不得为 FAILED 或 PARTIAL）。
2. 在隔离环境执行恢复测试：
   - 从备份文件恢复到空数据库实例。
   - 验证关键表行数一致（`captures`、`reviews`、`dispositions`）。
   - 随机抽取 100 条记录与原库比对摘要。
3. 验证对象存储备份：
   - 检查备份桶中对象数量与原桶一致。
   - 随机抽取 10 个对象比对 SHA-256 摘要。
4. 记录验证结果和时间。

### 3.2 恢复测试频率

- 完整恢复测试：每月一次。
- 摘要验证：每周一次。
- 备份作业状态检查：每日一次。
- 每次重大配置变更后额外执行一次恢复测试。

### 3.3 恢复失败处理

- 恢复测试失败立即升级至基础设施负责人。
- 查明原因前不得覆盖旧备份。
- 修复后重新执行完整恢复测试。

## 4. 证书轮换

### 4.1 设备证书轮换

1. 安全管理员签发新设备证书。
2. 在设备管理页面上传新证书，绑定相同 `device_id` 和 `station_id`。
3. 将新证书分发至工控机，更新采集代理配置指向新证书。
4. 重启采集代理，确认连接成功。
5. 吊销旧证书，验证旧证书无法建立连接。
6. 记录轮换事件。

### 4.2 服务证书轮换

1. 安全管理员签发新服务证书。
2. 将新证书和密钥部署至目标服务的机密存储。
3. 滚动重启目标服务实例（逐台重启，保持至少一台在线）。
4. 确认服务间 TLS 连接正常。
5. 吊销旧证书。
6. 记录轮换事件。

### 4.3 轮换检查

- 证书到期前 30 天触发告警。
- 到期前 7 天升级告警级别。
- 到期未轮换导致服务中断为 S1 事件。

## 5. 密钥轮换

### 5.1 数据库密码轮换

1. 在数据库中以管理员身份创建新密码。
2. 更新应用服务的机密存储中的数据库密码。
3. 逐台重启应用服务，确认数据库连接恢复。
4. 废弃旧密码。
5. 记录轮换事件。

### 5.2 对象存储密钥轮换

1. 在对象存储服务中创建新访问密钥。
2. 更新所有使用此密钥的服务的机密存储。
3. 逐台重启依赖服务，确认对象读写正常。
4. 禁用或删除旧访问密钥。
5. 验证签名地址仍然可用（如签名算法不依赖访问密钥则无需重启）。

### 5.3 轮换策略

- 所有密钥遵循企业密钥轮换策略规定的最大使用期限。
- 疑似泄露时立即轮换，不等待定期轮换窗口。
- 轮换期间至少保持一份有效凭据，避免因轮换造成服务中断。
- 轮换操作记录到审计日志。

## 6. 扩缩容与资源管理

### 6.1 推理服务扩容

- 增加推理实例前确认 GPU/CPU 资源可用。
- 新实例启动后等待模型加载完成，`/health` 确认就绪。
- 记录扩容原因、时间和新增实例数。

### 6.2 复核员扩容

- 当复核积压超过 50 且持续上升，通知质量负责人增派复核员。
- 在用户管理中为新增复核员创建账号并分配角色。
- 确认新复核员完成培训并对试复核任务的表现进行评估后再分配生产任务。

### 6.3 资源监控

- 持续监控 CPU、内存、GPU 显存、磁盘和网络使用率。
- 磁盘使用率达到 80% 时触发黄色告警，规划扩容或清理。
- GPU 显存使用率持续超过 90% 时评估是否需增加推理实例。
- 数据库连接池使用率超过 80% 时分析原因。

## 7. 日志分析

### 7.1 按 capture_id 追踪

从采集到最终处置的完整链路追踪：

1. **采集代理日志**：搜索 `capture_id` 确认采集时间、图像摘要和上传状态。
2. **业务后端日志**：搜索 `capture_id` 确认接收时间、入库记录和推理请求发送状态。
3. **消息队列**：确认该 `capture_id` 对应的推理请求已投递和消费。
4. **推理服务日志**：搜索 `capture_id` 确认模型加载、推理开始和完成时间、置信度分数和输出摘要。
5. **业务后端日志**：确认推理结果接收时间和处置决策。
6. **复核记录**：如有人工复核，确认复核详情和时间线。

### 7.2 日志查询命令

```bash
# 业务后端
docker compose logs business-api | grep "capture_id=xyz"

# 推理服务
docker compose logs inference | grep "capture_id=xyz"

# 采集代理（在工控机上）
journalctl -u defect-agent | grep "capture_id=xyz"
```

### 7.3 异常日志模式

| 模式 | 含义 | 参照手册 |
|------|------|----------|
| `disk full` / `no space` | 磁盘空间不足 | 01-disk-full.md |
| `connection refused` / `timeout` | 网络或服务不可达 | 02-network-outage.md |
| `dead letter` / `max retries` | 消息处理耗尽 | 03-dead-letter.md |
| `write error` / `readonly` | 数据库不可写 | 04-database-unwritable.md |
| `access denied` / `no such bucket` | 对象存储异常 | 05-object-storage.md |
| `model not loaded` / `no ready instance` | 模型未就绪 | 06-model-not-ready.md |
| `hash mismatch` / `digest verification` | 哈希冲突 | 07-hash-conflict.md |
| `review queue depth` | 复核积压 | 08-review-backlog.md |
| `backup failure` / `restore error` | 备份恢复异常 | 09-backup-restore.md |
| `coredump` / `OOM` | 服务崩溃需回滚 | 10-emergency-rollback.md |

## 8. 告警响应

### 8.1 告警映射

| 告警 | 严重级别 | 手册 | 首次响应时间 |
|------|----------|------|--------------|
| 磁盘使用率 > 90% | S1 | 01-disk-full.md | 5 分钟 |
| 网络中断 > 5 分钟 | S2 | 02-network-outage.md | 5 分钟 |
| 死信潮（1h > 50） | S2 | 03-dead-letter.md | 15 分钟 |
| 数据库不可写 | S1 | 04-database-unwritable.md | 立即 |
| 对象存储不可用 | S1 | 05-object-storage.md | 5 分钟 |
| 模型无就绪实例 | S1 | 06-model-not-ready.md | 立即 |
| 哈希校验失败 | S1 | 07-hash-conflict.md | 立即 |
| 复核积压 > SLA | S2 | 08-review-backlog.md | 15 分钟 |
| 备份作业失败 | S1 | 09-backup-restore.md | 30 分钟 |

### 8.2 告警响应流程

1. 确认告警：核对告警源、时间、影响范围，排除误报。
2. 分级响应：按手册严重级别启动对应的响应流程。
3. 只读检查：按手册执行只读检查，收集证据。
4. 恢复执行：按手册恢复步骤操作，记录每一步结果。
5. 恢复验证：按手册验证标准逐项确认。
6. 升级：超出手册权限或预计超过响应时间时及时升级。
7. 关闭：所有验证标准满足且证据完整后方可关闭告警。

### 8.3 告警静默

- 计划内维护期间可临时静默相关告警，设置明确的静默起止时间。
- 不得为通过验收或掩盖问题而静默告警。
- 静默操作需运维负责人批准，记录原因和时间。
