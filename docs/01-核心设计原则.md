# 核心设计原则

## 1. 文档职责

本文只规定所有模块共同遵守的架构原则和所有权边界。检测状态流转以 [02-完整检测业务流程](02-完整检测业务流程.md) 为准，字段和接口细节分别以数据库、接口文档为准。

## 2. 事实源唯一

1. PostgreSQL 保存采集、检测、复核、最终处置和发布审批等业务事实。
2. S3 兼容对象存储保存原图、掩膜、热图、模型和数据集文件。
3. 模型注册表保存模型技术版本、哈希、训练运行和评估证据。
4. RabbitMQ 只传递待执行事件，不能作为查询业务状态的依据。
5. 前端、本地 SQLite、缓存和搜索索引都是投影或副本，不得反向成为事实源。

跨系统需要复制信息时，必须同时保存源标识和源版本。例如业务库中的模型记录保存注册表地址、模型版本和制品哈希，而不是重新定义一套独立模型版本。

## 3. 边缘离线优先

车间网络短时中断不能造成已采集图片丢失：

- 采集端先把原图原子写入本地缓存，再把任务写入 SQLite。
- 每个 `capture_id` 在采集端生成，重试上传时保持不变。
- 中心接口必须幂等，允许同一任务至少一次送达。
- 只有中心确认图片校验通过且采集事件已提交后，本地记录才可进入可清理状态。
- 未上传或中心状态不确定的原图不得因缓存清理而删除。

离线能力只保证采集和补传，不承诺离线推理或离线人工复核。是否增加工控机本地推理属于后续独立决策。

## 4. 控制面与数据面分离

- 业务元数据、状态和审批走 Spring Boot 接口。
- 图片和模型大文件走受控上传或对象存储签名地址。
- 队列消息只携带对象引用、哈希、任务标识和版本，不携带图片二进制。
- 浏览器不直接拥有对象存储长期凭据，只取得短时、单对象、只读签名地址。

这样可以避免后端内存被大图占满，并使图片存储实现可以替换而不改变业务接口。

## 5. 原始事实不可变

1. 原图以首次通过校验的内容为准，只允许新增版本，不允许原位覆盖。
2. 算法结果、人工复核和最终处置分别记录，任何后续结论都不覆盖前一层证据。
3. 模型包、预处理配置和数据集版本一经发布不可修改；修正必须产生新版本。
4. 删除采用归档、保留期和受审计的清理任务，不使用业务代码直接物理删除。

## 6. 全链路版本化

每个检测结果必须能够回答：

- 使用了哪张原图及其 SHA-256。
- 使用了哪个预处理插件、插件版本和配置哈希。
- 使用了哪个算法插件、模型版本和模型制品哈希。
- 使用了哪个标准结果协议版本。
- 在哪个运行环境和哪次执行尝试中产生。

流水线版本由以上版本的不可变组合生成。不能只记录“当前模型”或目录名。

## 7. 安全失败

任何技术异常都不能被转换成“合格”：

- 图片损坏、校验失败、模型缺失、预处理失败和推理超时都进入 `HOLD` 或人工复核。
- 双任务模型判定不合格但掩膜为空时，保留不合格结论并强制复核，不能虚构缺陷位置。
- 算法判定合格但输出非空高分缺陷区域时，按结果矛盾处理。
- 中心状态未知时，采集端保留原图并继续补传，不能假定成功。

自动放行必须由版本化规则引擎依据已成功的算法结果作出，不能由前端或采集端自行决定。

## 8. 算法与业务解耦

算法插件只接收标准化内存对象并返回标准化结果：

- 不直接访问业务数据库。
- 不直接消费或发布业务队列。
- 不根据生产角色或工单状态改变推理逻辑。
- 不自行生成最终生产处置。
- 不把本地绝对路径暴露到业务结果。

业务后端负责任务、幂等、处置、复核和审计；推理服务负责加载模型、预处理、执行和结果规范化。

## 9. 训练与在线推理解耦

生产服务禁止边检测边更新权重。所有增量训练都走：

`候选样本 -> 人工确认 -> 数据集版本 -> 离线训练 -> 固定测试评估 -> 审批 -> 灰度 -> 正式发布`

生产模型只从已批准的不可变版本启动。回滚是重新指向旧版本并重启或热切换运行槽，不是覆盖文件。

## 10. 可审计和可观测

`capture_id`、`detection_task_id` 和 `trace_id` 必须贯穿采集端、网关、后端、队列、推理和复核。

- 日志用于解释具体事件。
- 指标用于发现趋势和服务水平问题。
- 链路追踪用于定位跨服务耗时。
- 审计日志用于回答谁在何时做了什么变更。

业务审计和运行日志不能互相替代。

## 11. 最小权限和职责分离

- 采集端只能写本工位采集数据和查询本工位结果。
- 推理服务只能读任务引用、读模型与原图、写派生结果。
- 算法工程师可以训练和登记候选模型，但不能单人发布生产模型。
- 系统管理员维护系统，不默认拥有质量结论修改权限。
- 高权限操作启用多因素认证、二次确认和不可篡改审计。

具体角色矩阵见 [12-安全权限与角色](12-安全权限与角色.md)。

## 12. 先模块化单体，后按压力拆分

中心业务首期采用模块化单体 Spring Boot 应用，数据库保持一个业务事实源；推理服务因运行时、GPU 和扩缩容要求独立部署。暂不为设备、复核、数据集分别建设微服务。

只有出现以下证据后才拆分业务服务：

1. 独立扩缩容需求持续存在。
2. 发布节奏或故障域确实需要隔离。
3. 模块边界和接口已稳定。
4. 团队具备分布式事务、配置和监控运维能力。

## 13. 配置与代码分离

以下内容必须配置化并版本化：

- 工位、相机、曝光、触发去抖和采集超时。
- 自动放行、强制复核、抽检和升级复核规则。
- 队列重试次数、超时和并发。
- 预处理参数、模型阈值和流水线组合。
- 文件大小、格式、保留期和签名地址有效期。
- 监控阈值和服务目标。

配置变更需要校验、审计、灰度和回滚。前端不得保存只有浏览器知道的业务配置。

## 14. 当前项目特有约束

1. 现有 TensorFlow 2.13、Keras 2.13.1 和 Python 3.11 环境应先原样封装，模型兼容性验证前不升级核心运行时。
2. 当前加载器启用了不安全反序列化，只能加载来源可信且哈希已登记的模型；生产化前应增加签名、白名单和隔离。
3. `outputs/training` 中的三个双任务产物必须分别评估和登记，不能仅凭目录名确定生产模型。
4. 当前 34 张测试样本适合做项目内配对比较，不足以单独证明车间全场景上线质量。
5. 当前极坐标模型版本与代码不兼容，重新标定后才能进入注册表。
6. 原始图片和当前输出体量较大，图片不得写入数据库，也不得通过队列传输。
