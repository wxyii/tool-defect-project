# 日志与监控

## 1. 文档职责

本文定义结构化日志、指标、链路追踪、看板、告警和运行可见性。错误是否重试由 [10-异常处理](10-异常处理.md) 决定。

## 2. 三类记录

| 类型 | 回答的问题 | 典型保存位置 |
|---|---|---|
| 运行日志 | 某次请求或任务发生了什么 | 日志平台 |
| 指标 | 系统是否正在变差 | Prometheus |
| 审计日志 | 谁对什么资源做了什么受控操作 | 业务数据库和防篡改归档 |

审计日志不能仅依赖普通应用日志，因为普通日志会轮转、采样和调整级别。

## 3. 结构化日志

所有服务输出 JSON，每条至少包含：

```json
{
  "timestamp": "2026-07-28T10:30:02.123Z",
  "level": "INFO",
  "service": "inference-service",
  "service_version": "git-sha-or-build-id",
  "environment": "production",
  "host": "worker-gpu-01",
  "event": "inference.completed",
  "message": "推理完成",
  "request_id": "019f...",
  "trace_id": "32位值",
  "span_id": "16位值",
  "capture_id": "019f...",
  "detection_task_id": "019f...",
  "attempt_id": "019f...",
  "station_id": "019f...",
  "pipeline_version": "production-r8/12",
  "model_version": "multitask/3",
  "duration_ms": 346.2,
  "result": "SUCCESS",
  "error_code": null
}
```

### 3.1 事件命名

使用稳定的 `领域.动作`：

```text
capture.persisted
upload.completed
outbox.published
inference.started
inference.completed
inference.failed
review.submitted
model.loaded
model.deployed
model.rolled_back
```

文案可以修改，事件名保持稳定。

### 3.2 禁止记录

- 原图、掩膜和 Base64 内容。
- 访问令牌、刷新令牌、Cookie、私钥和签名地址完整查询串。
- 数据库密码、对象存储密钥和相机密码。
- 完整模型文件或训练数据。
- 无必要的用户个人信息。

绝对本地路径只允许在受限调试日志中短期出现，生产日志优先记录对象键或逻辑标识。

### 3.3 异常日志

错误日志记录：

- 稳定错误码。
- 阶段。
- 是否可重试。
- 尝试次数。
- 受影响资源标识。
- 脱敏异常类型。
- 堆栈只进入受限日志流，不返回前端。

同一持续错误应做速率限制和聚合，避免日志风暴。

## 4. 分布式追踪

使用 W3C `traceparent` 贯穿：

`采集请求 -> Nginx -> 后端 -> 发件箱 -> RabbitMQ -> 推理 -> 对象存储 -> 结果回调 -> 复核`

队列生产者把追踪上下文放入消息头，消费者创建 `CONSUMER` span 并链接生产 span。核心 span：

- `edge.capture.persist`
- `http.upload.initialize`
- `storage.put`
- `outbox.publish`
- `queue.wait`
- `preprocess.run`
- `model.infer`
- `artifact.upload`
- `result.commit`
- `review.submit`

图片下载和模型推理必须分开计时，避免把存储慢误判为模型慢。

## 5. 指标命名

统一前缀 `tool_defect_`。计数器以 `_total` 结尾，时长使用秒并以 `_seconds` 结尾，字节使用 `_bytes`。

示例：

```text
tool_defect_edge_captures_total
tool_defect_edge_queue_depth
tool_defect_inference_duration_seconds
tool_defect_inference_failures_total
tool_defect_storage_upload_bytes_total
```

Prometheus 标签禁止放 `capture_id`、`task_id`、用户标识、对象键和错误全文等高基数字段。这些标识只放日志和追踪。

## 6. 组件指标

### 6.1 采集端

- 采集总数和失败数，按工位、设备类型和错误类别。
- 本地队列深度、最老任务年龄。
- 待上传和待结果数量。
- 本地磁盘使用率和可用字节。
- 相机在线、PLC 在线、中心连接状态。
- 上传吞吐、失败和重试。
- 工控机时钟偏差。
- 采集代理版本信息。

### 6.2 Nginx 和业务后端

- HTTP 请求速率、状态码和延迟。
- 当前连接和上传请求大小。
- 数据库连接池使用率和等待时间。
- 事务失败、死锁和慢查询。
- 发件箱未发布数量和最老事件年龄。
- 采集状态分布和状态停留时间。
- 服务器发送事件连接数和断线数。

### 6.3 RabbitMQ

- 每队列就绪、未确认和重投消息数。
- 消息发布确认失败。
- 消费速率和积压年龄。
- 死信队列消息数。
- 节点磁盘、内存水位和连接状态。

### 6.4 推理服务

- 工作进程就绪状态。
- 当前加载模型、模型加载和预热耗时。
- 各流水线请求、成功、失败和不确定数量。
- 下载、解码、预处理、推理、后处理和上传分阶段直方图。
- 缓存命中、重建和损坏数量。
- CPU、内存、GPU 利用率、显存和温度。
- 输入尺寸与图片格式分布。
- 插件错误码。

### 6.5 图片存储

- 上传和下载请求、延迟、错误。
- 存储使用量、对象数量和增长率。
- 哈希校验失败。
- 暂存和孤儿对象数量。
- 生命周期删除失败。
- 备份或复制延迟。

### 6.6 复核

- 各优先级待办数量。
- 最老等待时间和超时数量。
- 认领、释放和租约过期。
- 复核耗时。
- 双人不一致数量。
- 模型推翻和掩膜修订比例。

### 6.7 数据与模型

- 候选样本池数量和年龄。
- 数据集构建成功、失败、冲突和泄漏数。
- 训练运行状态、耗时和资源。
- 当前生产和灰度模型信息。
- 模型加载失败和回滚。
- 结论分布、置信度分布和预处理失败率变化。

业务质量指标必须注明真值来源和最小样本量。

## 7. 服务目标

在现场节拍未确认前，先定义计算方式，不伪造最终数值：

| 目标 | 计算 |
|---|---|
| 在线采集接收可用性 | 成功接受的合法请求数除以合法请求总数 |
| 端到端检测延迟 | 从中心确认原图到产生自动处置的时间 |
| 最终处置延迟 | 从采集到自动或人工最终处置的时间 |
| 推理成功率 | 成功标准结果数除以开始执行数，重复消息不重复计数 |
| 补传成功率 | 断网任务在恢复窗口内成功同步的比例 |
| 复核时限达标率 | 在对应优先级时限内关闭的任务比例 |

初始建议：

- 在线生产时段控制面可用性目标不低于 99.9%。
- 自动检测端到端 P95 必须小于现场允许节拍，并保留至少 20% 余量。
- 原图确认后数据丢失目标为 0。

以上数值必须在硬件压测和现场试运行后由业务签字冻结。

## 8. 告警基线

| 严重度 | 条件示例 | 动作 |
|---|---|---|
| 严重 | 工控机磁盘超过 95%、生产模型无就绪实例、数据库不可写、发现哈希冲突 | 立即通知值班人员，必要时暂停现场 |
| 高 | 设备心跳超过 2 分钟缺失、死信队列非空、任务最老年龄超过现场时限、推理失败率 10 分钟内超过 5% 且样本不少于 100 | 通知运维、质量或算法负责人 |
| 中 | 磁盘超过 90%、发件箱积压、复核任务临近时限、备份延迟 | 在工作时间处理 |
| 低 | 版本落后、容量趋势预警、少量可恢复重试 | 进入待办 |

阈值按环境配置。没有足够样本时使用绝对失败数和连续失败判断，避免小分母误报。

质量告警示例：

- 自动 `PASS` 抽检中人工 `FAIL` 比例显著上升。
- 某工位预处理失败率超过自身历史基线。
- 新模型与稳定模型影子结论分歧升高。
- 置信度分布或图片质量分布漂移。

这些告警只触发调查或提高复核比例，不自动训练和发布模型。

## 9. 看板

### 9.1 现场运行

工位在线、相机和 PLC、本地队列、磁盘、最近采集和最终处置。

### 9.2 中心服务

API、数据库、发件箱、队列、对象存储和推理健康。

### 9.3 推理性能

各模型版本的吞吐、分阶段延迟、失败、显存和缓存。

### 9.4 质量与复核

处置分布、抽检、推翻、复核积压、图片质量和模型漂移。

### 9.5 训练与发布

候选数据、训练状态、评估门禁、灰度表现、当前模型和回滚事件。

每个看板提供时间范围、环境、工位和模型筛选，并链接到日志和追踪。

## 10. 日志和追踪保留

建议基线：

- 普通运行日志在线保留 30 天，归档 180 天。
- 错误和安全日志在线保留 90 天，按合规要求归档。
- 全量追踪短期保留，成功链路可采样，错误和高延迟链路全保留。
- 审计日志按质量与安全要求长期保留并做防篡改归档。

保留期最终由存储、质量、安全和法务共同确认。

## 11. 采样

- 错误、模型加载、发布、回滚和安全事件不采样。
- 普通成功 HTTP 和推理链路可按比例采样。
- 高延迟链路使用尾部采样保留。
- 日志采样不能影响计数指标。

## 12. 时间同步

- 中心服务器、工控机、相机控制器和 PLC 网关使用统一时间源。
- 采集端上报与中心的时钟偏差。
- 偏差超限时保留原始设备时间和接收时间，并产生告警。
- 业务排序优先使用采集时间，审计排序同时参考中心接收时间。

## 13. 当前代码接入

当前 Python 命令行主要打印文本和写 CSV/JSON。工程化时：

1. 增加统一结构化日志适配器。
2. 保留现有 CSV、报告作为离线制品，不把它们当在线日志。
3. 为 `predict`、环形预处理、极坐标检测、训练和评估分别增加阶段计时。
4. 把缓存命中、模型版本、输入尺寸和结果状态作为结构字段。
5. 捕获异常并转换为标准错误码，但保留原异常链在受限日志。

## 14. 验收

- 从一个 `capture_id` 能关联采集、接口、队列、推理、存储和复核日志。
- 指标中没有高基数任务标识。
- 日志不包含令牌、签名地址和图片内容。
- 生产模型未就绪、死信、磁盘高水位和数据库故障均能告警。
- 告警恢复后自动关闭或标记恢复，并保留处置记录。
- 备份恢复演练和监控失明都有独立可见性。
