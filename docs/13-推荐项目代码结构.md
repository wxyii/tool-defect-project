# 推荐项目代码结构

## 1. 文档职责

本文定义目标仓库布局、模块所有权、依赖方向、契约位置和从当前仓库的迁移顺序。具体技术产品和版本见 [14-技术选型](14-技术选型.md)。

## 2. 仓库策略

首期采用单一仓库，原因是：

- 当前团队和代码规模适合集中管理。
- 采集、后端、前端和推理需要同步演进契约。
- 可以统一版本、测试、文档和部署清单。
- 模块边界仍在形成，过早拆仓会增加协调成本。

数据、图片、权重、模型包和运行输出不进入 Git，通过对象存储、数据集版本和模型注册表管理。

## 4. 当前代码映射

| 当前路径 | 目标归属 | 处理方式 |
|---|---|---|
| `src/tool_defect/data` | `packages/tool-defect-core` | 保留算法无关的数据加载和几何处理 |
| `src/tool_defect/detection` | 核心包与推理插件 | 核心计算留在包内，插件包装生命周期和协议 |
| `src/tool_defect/models` | `packages/tool-defect-core` | 保留模型构建和可信模型加载 |
| `src/tool_defect/inference` | 核心推理与服务编排 | 拆分纯函数和文件写出逻辑 |
| `src/tool_defect/training` | `jobs/training-pipeline` 与核心包 | 训练入口进入任务，损失和序列可留核心包 |
| `src/tool_defect/evaluation` | `jobs/model-evaluator` | 改为接收数据集版本和模型版本 |
| `src/tool_defect/cli.py` | 核心包维护 CLI | 继续作为开发、离线和诊断入口 |
| `app/legacy` | `legacy/` 或归档 | 只读保留，不进入生产依赖 |
| `configs` | 核心算法示例配置 | 生产配置迁入受控配置和模型包 |
| `data` | 对象存储和数据集版本 | Git 只保留小型测试样例 |
| `outputs/training` | 模型迁移暂存来源 | 登记后由模型注册表管理 |
| `artifacts` | 历史结构与小型示例 | 不再作为生产“当前模型”目录 |

迁移不是一次性改路径。先加服务包装和契约，再在测试保护下抽取核心包。

## 5. 业务后端模块

Spring Boot 首期是模块化单体。每个业务模块内部采用：

```text
module/
├── api/             HTTP 输入输出
├── application/     用例和事务边界
├── domain/          实体、值对象和规则
└── infrastructure/  数据库、队列和外部适配
```

依赖方向：

```text
api -> application -> domain
infrastructure -> application/domain
domain 不依赖 Spring、数据库和消息队列
```

模块之间通过应用服务或领域事件交互，禁止直接访问其他模块的数据访问层。

数据库迁移由 `business-api` 唯一拥有。推理、训练和前端不能各自创建业务表。

## 6. Python 核心包边界

`tool-defect-core` 只包含可离线测试的计算：

- 图片和掩膜解码。
- 环形几何与极坐标预处理。
- 模型结构、可信加载和预测。
- 损失、训练序列和评估指标。
- 标准结果转换所需的纯函数。

不放入核心包：

- FastAPI 路由。
- RabbitMQ 消费者。
- 对象存储凭据。
- 业务数据库访问。
- 用户权限。
- 生产配置获取。

这样现有 CLI、训练任务和在线推理可以复用同一计算实现。

## 7. 推理服务边界

推理服务负责：

- 队列消费和幂等。
- 对象下载与校验。
- 插件发现、加载、预热和关闭。
- 模型运行槽和资源控制。
- 派生文件写入。
- 标准结果回调。
- 健康、指标和追踪。

算法插件不能反向导入 `consumer`、`storage` 或 `api`。

## 8. 采集客户端边界

采集端分为：

- `adapters/cameras`：工业相机厂商适配。
- `adapters/triggers`：PLC、传感器、数字量或协议适配。
- `capture`：触发去抖、帧组合和质量门禁。
- `local_queue`：SQLite、状态和迁移。
- `sync`：中心接口、上传和对账。
- `health`：心跳、磁盘和设备状态。

厂商软件开发包不得渗透到同步和业务逻辑。更换相机只替换适配器。

## 9. 前端结构

按业务功能而不是文件类型堆放页面：

```text
features/reviews/
├── api.ts
├── routes.ts
├── store.ts
├── types.ts
├── components/
└── views/
```

通用图片查看和标注组件放 `components/image-workbench`，业务复核规则仍留在 `features/reviews`。

生成的接口客户端放 `src/api/generated`，禁止手工修改；扩展封装放 `src/api/client`。

## 10. 契约所有权

- `contracts/openapi` 是 HTTP 字段和状态枚举源。
- `contracts/asyncapi` 和 `json-schema` 是消息源。
- 生成后的 Java、Python 和 TypeScript 类型只提交或发布生成产物，不在三处手写同一模型。
- 示例报文在持续集成中做模式校验。
- 插件内部 Python 类型不直接暴露为网络契约。

## 11. 配置结构

仓库只保存：

- 配置模式。
- 无敏感信息的默认值。
- 开发和测试示例。

环境目录保存对配置版本的引用，不保存密码。生产配置由配置中心或部署机密注入。

算法配置进入流水线版本和模型包；工位配置进入业务配置版本；两者不能共用一个无边界的大型 JSON。

## 12. 测试结构

### 12.1 单元测试

- Python 核心计算。
- Java 领域规则。
- Vue 组件和状态。
- 采集状态机。

### 12.2 契约测试

- OpenAPI 兼容性。
- 事件模式。
- Java 后端与 Python 推理消费者契约。
- 采集端幂等和对账。

### 12.3 集成测试

- PostgreSQL、RabbitMQ 和对象存储使用容器化测试依赖。
- 模型服务使用小型固定模型和图片。
- 验证事务发件箱、重复消息和对象最终一致。

### 12.4 端到端测试

模拟 PLC 触发到最终处置，包括断网、重试、复核、模型切换和回滚。

### 12.5 模型回归测试

固定测试集、固定模型哈希和容差，验证输入输出、掩膜、指标和性能。

## 13. 构建和发布

每个可部署单元有独立构建文件和容器镜像：

- `edge-agent` 可生成 Windows 安装包或服务包。
- `web-console` 生成静态资源。
- `business-api` 生成可执行包和容器。
- `inference-service` 生成 CPU 与 GPU 镜像。
- 训练任务使用与生产推理分开的镜像。

镜像标签使用版本和代码提交，不使用可变的 `latest` 作为生产部署依据。

## 14. 代码所有权

建议设置：

- 采集与设备负责人。
- 业务后端负责人。
- 前端与复核交互负责人。
- 算法核心和训练负责人。
- 推理运行时负责人。
- 数据和模型发布负责人。
- 基础设施与安全负责人。

跨边界改动必须由对应所有者审查。契约变更至少需要生产方和消费方共同审查。

## 15. 分阶段迁移

### 阶段一：不搬现有核心

1. 保持 `src/tool_defect` 和现有 CLI 可用。
2. 新增 `contracts`。
3. 新增推理服务外壳，通过适配器调用当前包。
4. 新增后端、前端和采集端骨架。
5. 把权重按 [08-增量训练闭环](08-增量训练闭环.md) 登记。

### 阶段二：抽取核心包

1. 区分纯计算和文件系统副作用。
2. 把纯计算移动到 `packages/tool-defect-core`。
3. CLI、推理和训练都依赖该包。
4. 保留兼容导入或一次性迁移说明。

### 阶段三：工程化闭环

1. 数据集构建和训练进入独立任务。
2. 引入模型注册、灰度和回滚。
3. 去除生产对根目录 `outputs` 和 `artifacts` 的依赖。

### 阶段四：按证据扩展

只有吞吐、故障域或团队发布节奏证明需要时，才拆分 Spring Boot 业务模块或引入 Kubernetes。

## 16. 禁止项

- 把模型权重提交 Git。
- 让后端直接导入 Python 算法代码。
- 让推理服务直连业务数据库。
- 在前端复制业务判定规则。
- 把对象存储路径当作永久公开 URL。
- 用目录名代替模型版本。
- 在一个共享 `utils.py` 中堆放跨域逻辑。
- 在同一运行环境混装训练和生产推理依赖。
- 未有测试保护就一次性移动全部现有代码。
