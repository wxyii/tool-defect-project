# 技术选型

## 1. 文档职责

本文给出目标系统的技术栈、版本基线、理由、替代方案和暂不采用项。核验日期为 2026-07-28；正式部署时必须重新确认安全补丁和支持周期，并锁定精确补丁版本。

## 2. 选型原则

1. 保留当前 Python 3.11、TensorFlow 2.13 和 Keras 2.13.1 的模型兼容环境。
2. 业务系统采用成熟、可维护的企业后端和关系数据库。
3. 边缘能离线排队，中心采用可靠消息和幂等消费。
4. 图片、样本导出包和模型使用 S3 兼容接口，避免绑定单一厂商。
5. 首期单中心、模块化单体和容器编排，不引入不必要的 Kubernetes。
6. 选择仍在维护、许可证和支持方式清晰的组件。

## 3. 推荐技术栈

| 层 | 推荐 | 说明 |
|---|---|---|
| 工控机采集 | Python 3.11、SQLite WAL、HTTPX、OpenCV、厂商软件开发包 | 复用当前 Python/OpenCV 能力，独立于 TensorFlow 环境 |
| 工控机运行 | Windows 服务或 Linux systemd，按相机软件开发包决定 | 不使用 PyQt 作为生产采集主进程 |
| 网关 | Nginx 稳定受支持版本 | TLS、路由、限流、大文件数据面 |
| 中心后端 | Java 25 长期支持版、Spring Boot 4.1.x、Maven | 生产级业务、权限、事务、健康和指标 |
| 数据库 | PostgreSQL 18 当前补丁版、Flyway | 业务事实、JSONB、审计、可靠事务 |
| 消息队列 | RabbitMQ 4.x 当前受支持系列、仲裁队列 | 持久任务、手动确认、死信和路由 |
| 推理服务 | Python 3.11、FastAPI、Uvicorn、Pydantic 2 | 健康与内部接口；任务由队列工作进程执行 |
| 算法运行 | TensorFlow 2.13.0、Keras 2.13.1、OpenCV 4.11、NumPy 1.24.3 | 与当前模型和代码兼容，先不升级 |
| 对象存储协议 | S3 兼容接口 | 原图、派生图、样本导出包、隔离模型包和已发布模型 |
| 自托管对象存储 | 已有企业存储优先；绿地小中型部署优先评估 SeaweedFS 4.x | 需完成可靠性、S3 兼容和运维验收 |
| 模型制品管理 | PostgreSQL 模型元数据、S3 隔离模型包、独立验证进程 | 支持外部模型直接上传、来源证据、验证、发布和回滚，不管理训练运行 |
| 前端 | Vue 3、TypeScript、Vite、Pinia、Vue Router、Element Plus、ECharts | 车间与管理后台统一网页 |
| 前端构建 | Node.js 24 长期支持版、pnpm | 只在构建环境使用 |
| 身份 | 人员本地账号会话；设备和服务使用独立机器身份 | Spring Security |
| 可观测 | OpenTelemetry、Prometheus、Grafana、Loki、Tempo | 日志、指标和追踪统一关联 |
| 部署 | Docker Engine 与 Compose；GPU 主机使用受控 NVIDIA 运行时 | 单中心首期足够，生产镜像不可变 |
| 测试 | pytest、JUnit 5、Testcontainers、Vitest、Playwright | 单元、契约、集成和端到端 |

## 4. 工控机采集端

### 4.1 选择 Python 3.11

优点：

- 当前算法和旧界面已使用 Python、OpenCV 和摄像头访问。
- SQLite、文件校验、HTTP 和厂商原生库封装成熟。
- 减少首期语言数量和团队切换成本。

生产采集进程不能安装 TensorFlow、Matplotlib 等重依赖，单独维护轻量锁文件。

### 4.2 硬件适配例外

PLC 和工业相机型号尚未确认，协议不提前锁死：

- 相机有官方 Python 或 C 软件开发包时，使用 Python 适配器。
- 厂商只支持 .NET 且生产支持明显更好时，可以实现薄 .NET 硬件侧车，通过本机命名管道或受限本地接口向采集主进程提供标准帧。
- OPC UA、Modbus TCP、数字量或厂商协议均实现为 `TriggerAdapter`。

硬件语言例外不能改变中心接口、`capture_id` 和本地队列语义。

### 4.3 不采用旧 PyQt 主程序

旧 PyQt 平台把摄像头、文件选择、模型加载、训练和展示放在同一桌面进程，缺少 PLC、离线队列、中心审计和权限边界。它只用于参考摄像头和交互，不作为生产基础。

## 5. 中心业务后端

### 5.1 Java 25 和 Spring Boot 4.1

Java 25 是长期支持版本；Spring Boot 4.1 是核验日官方稳定版本，最低需要 Java 17。选择 Java 25 可以获得更长的维护窗口。官方资料：

- [Java 长期支持路线](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)
- [Spring Boot 官方文档](https://docs.spring.io/spring-boot/)

核心依赖：

- Spring Web。
- Spring Security OAuth2 资源服务器。
- Spring Data JPA。
- Spring AMQP。
- Spring Boot Actuator。
- Flyway。
- PostgreSQL JDBC 驱动。
- Micrometer 和 OpenTelemetry。
- OpenAPI 生成或文档组件。

首期采用模块化单体，不采用多业务微服务。

### 5.2 Java 版本替代

若企业 Java 运行平台只能支持 Java 21，可以使用 Java 21 长期支持版，但必须确认所选 Spring Boot 精确版本、构建工具和安全支持周期。不能因为本地已有旧 JDK 就退回已停止支持版本。

## 6. PostgreSQL

选择 PostgreSQL 18 的当前补丁版。官方版本策略为每个主版本支持 5 年，且建议始终运行该主版本的当前小版本。核验日 PostgreSQL 18 受支持至 2030 年：

- [PostgreSQL 版本策略](https://www.postgresql.org/support/versioning/)

采用：

- 主从或受管高可用视现场条件决定。
- `pgBackRest` 或企业备份工具。
- Flyway 模式迁移。
- 连接池、慢查询和备份恢复监控。

不使用 SQLite 作为中心数据库；SQLite 只用于工控机本地队列。

## 7. RabbitMQ

选择 RabbitMQ 4.x 在部署时仍受支持的系列和当前补丁。核验日 4.3 为最新完整社区支持系列，但社区支持窗口较短，项目必须把系列升级纳入运维计划；需要长期厂商支持时采购对应支持服务。

- [RabbitMQ 发布与支持信息](https://www.rabbitmq.com/release-information)
- [RabbitMQ 升级路径](https://www.rabbitmq.com/docs/upgrade)

配置基线：

- 仲裁队列。
- 持久消息。
- 发布者确认。
- 消费者手动确认。
- 死信交换机。
- 在线、影子和批量任务隔离。
- 管理端口只在管理网络开放。

不选 Redis 列表作为生产推理队列，因为本方案需要明确的投递确认、路由、死信和运维边界。Redis 可在未来有独立缓存需求时再引入。

## 8. Python 推理服务

### 8.1 保持当前模型环境

当前仓库实际环境：

```text
Python 3.11.14
TensorFlow 2.13.0
Keras 2.13.1
OpenCV 4.11.0
NumPy 1.24.3
Pandas 2.0.3
```

生产首版锁定这些核心版本。框架升级单独建立兼容项目，必须验证：

- 三个现有双任务模型。
- 模型 JSON 反序列化。
- 自定义 CBAM 层。
- 预处理像素一致性。
- 固定测试集指标和性能。

### 8.2 FastAPI

FastAPI 只承载健康、模型元数据和内部结果接口；推理任务由 RabbitMQ 消费者编排。利用应用生命周期在启动时加载和关闭模型，官方文档也建议用生命周期管理机器学习模型：

- [FastAPI 应用生命周期](https://fastapi.tiangolo.com/advanced/events/)
- [FastAPI 多进程部署](https://fastapi.tiangolo.com/deployment/server-workers/)

GPU 场景通常一个容器进程对应一个模型工作进程，不盲目开启多个 Web 工作进程复制显存。

### 8.3 环境拆分

- `inference-cpu.lock`。
- `inference-gpu.lock`。
- `model-validator.lock`。
- `edge.lock`。

生产部署基线不提供 `training.lock`、训练服务或训练调度器。外部训练环境由系统边界外独立管理，不能与生产推理或模型隔离验证共用可变虚拟环境，也不能成为在线业务依赖。

## 9. 对象存储

### 9.1 协议优先

业务只绑定 S3 兼容协议。部署优先级：

1. 公司已有、已有备份和运维团队的 S3 兼容存储。
2. 绿地小中型自托管环境评估 SeaweedFS，完成版本、权限、生命周期、备份和故障演练后采用。
3. 公司已有 Ceph 集群时使用 Ceph RGW。
4. 需要商业服务等级时采购受支持对象存储。

SeaweedFS 当前仍维护、采用 Apache 许可证并提供 S3 接口：

- [SeaweedFS 项目说明](https://github.com/seaweedfs/seaweedfs)

Ceph RGW 支持 S3 数据访问模型、对象版本和生命周期等能力：

- [Ceph 对象网关的 S3 接口](https://docs.ceph.com/en/latest/radosgw/s3/)

### 9.2 不默认选社区 MinIO

MinIO 社区仓库在 2026-04-25 已归档，社区版改为仅源码分发且使用 AGPLv3。除非选择有明确商业支持的产品并通过许可证审查，否则不把社区 MinIO 作为新系统默认生产基线：

- [MinIO 社区仓库现状](https://github.com/minio/minio)

开发测试可以使用本地文件适配器或与生产相同协议的临时测试实例，但不能据此跳过生产存储验收。

## 10. 模型元数据、隔离存储与独立验证

### 10.1 在线职责边界

在线系统只负责：

- 管理员通过浏览器直接上传外部模型包。
- 在 PostgreSQL 记录上传会话、模型版本、外部来源证据、验证结果、审批和部署历史。
- 在 S3 隔离前缀保存待验证的不可变模型包，并在验证通过后按状态转入可发布区域。
- 由独立验证进程执行格式、哈希、签名、依赖白名单、安全扫描和固定样例验证。
- 发布已验证模型并保留可审计回滚目标。

模型记录不要求内部数据集版本或内部训练运行外键。外部来源证据至少包含提供方、生成时间、适用范围、评估摘要、软件环境和制品哈希；证据或验证结果不完整时模型保持 `HOLD`，不能发布。

### 10.2 存储和验证隔离

- 待验证模型包只能写入 S3 隔离前缀，推理服务不能读取该前缀。
- 模型验证进程通过对象级短期只读授权读取一个模型包，不持有业务数据库、消息队列或生产对象存储写凭据。
- 验证容器无外网、非特权、只读根文件系统，并限制 CPU、内存、显存、进程和临时空间。
- 业务后端根据验证结果和管理员审批修改模型状态；任何技术失败、来源未知或哈希冲突都进入 `HOLD`，不得产生可发布状态。

### 10.3 与外部训练的人工交接

样本整理完成后，在线系统生成带清单和哈希的样本导出包，由授权管理员人工交给外部训练环境。外部环境独立完成数据组织、训练和评估，再把模型包及来源证据交给管理员，通过在线系统的直接上传入口进入隔离区。

外部训练平台没有业务数据库、生产对象存储、RabbitMQ 或内部服务凭据。在线系统不接收外部训练任务状态、进度、日志或事件，也不依赖其接口、回调和可用性。生产技术栈不引入实验跟踪或内部训练编排平台。

- Pinia。
- Vue Router。

## 12. 身份和权限

人员身份由业务后端管理本地账号、`Argon2id` 哈希和数据库会话；设备与服务身份
保持独立，不允许人员账号用于机器调用。

Spring Boot 验证用户令牌和权限；设备使用双向 TLS 和客户端凭据。对象存储、RabbitMQ、数据库和监控分别使用服务身份。

## 13. 可观测

OpenTelemetry 负责统一生成和导出日志、指标和追踪，但它不是存储后端。后端组合：

- Prometheus：指标。
- Grafana：统一可视化。
- Loki：结构化日志。
- Tempo：追踪。
- OpenTelemetry Collector：接收、处理和转发。

- [OpenTelemetry 定义](https://opentelemetry.io/docs/what-is-opentelemetry/)
- [Prometheus 指标命名](https://prometheus.io/docs/practices/naming/)

如果企业已有监控平台，保留 OpenTelemetry 和 Prometheus 兼容出口，复用现有后端。

## 14. 部署

### 14.1 首期

单中心使用 Docker Engine 与 Compose：

- Nginx。
- Spring Boot。
- RabbitMQ。
- PostgreSQL。
- 对象存储。
- 推理 CPU 或 GPU 工作进程。
- 模型隔离验证进程。
- 监控组件。

生产容器使用非根用户、只读根文件系统、资源限制和不可变镜像。Docker 官方说明 rootless 模式可以降低守护进程权限风险，业务与监控容器在兼容时优先采用：

- [Docker rootless 模式](https://docs.docker.com/engine/security/rootless/)

GPU 主机若 rootless 与设备运行时不兼容，仍要求容器内非根用户、禁止特权模式、最小设备映射和独立主机加固。

### 14.2 暂不采用 Kubernetes

当前数据量、团队规模和单中心架构没有证明需要 Kubernetes。出现多节点自动扩缩容、多中心容灾、频繁独立发布或企业已有成熟平台时再评估。

## 16. 许可证和供应链

上线前为每个组件和厂商软件开发包记录：

- 许可证。
- 来源和下载地址。
- 精确版本和 SHA-256。
- 支持结束时间。
- 已知漏洞。
- 软件物料清单。

模型、容器和依赖都必须可追溯。任何已停止维护、来源不明或许可证不适合企业使用的组件都不能仅因“本地能跑”进入生产。

## 17. 需要现场确认后才能锁定的选项

| 选项 | 依赖信息 |
|---|---|
| Windows 或 Linux 工控机 | 相机和 PLC 官方驱动 |
| Python 直连或 .NET 硬件侧车 | 厂商支持语言和稳定性测试 |
| SeaweedFS、Ceph RGW 或企业对象存储 | 现有基础设施、节点数、支持和许可证 |
| CPU 或 GPU 推理 | 节拍、模型时延和并发 |
| 单机或高可用 PostgreSQL、RabbitMQ | 停机容忍、恢复目标和预算 |
| 本地账号与数据库会话 | 人员身份系统 |
| Compose 或企业容器平台 | 运维能力和已有平台 |

这些选择锁定后写入部署决策记录，不修改本方案中稳定的业务和接口边界。
